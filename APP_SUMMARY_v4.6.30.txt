🧭 1. WHAT THE APP IS (THE BIG PICTURE)
================================================================================

A Windows desktop trading app (PyQt6, packaged with PyInstaller --onedir) that
runs AI-driven trading bots against the Alpaca API (paper + live). It is backed
by a FastAPI server on Oracle Cloud that adds accounts, cloud bot execution,
a bot marketplace, a phone web dashboard, a credits economy, friends, and
moderation.

THE CORE PITCH (what should draw users — keep this front of mind):
  1. Trade MANUALLY against your friends (rivalry / leaderboards).
  2. Build / buy / sell trading BOTS on a marketplace and earn credits.

Three pieces fit together:
  • DESKTOP APP  — the control room (overview, per-bot tabs, make-bot, manual
    trading, friends, account, admin, universe, tools).
  • ORACLE SERVER — auth, encrypted broker creds, 24/7 cloud bot running,
    marketplace, web dashboard, credits/revenue, moderation, scheduler.
  • WEBSITE       — landing page + phone-friendly dashboard showing PLATFORM-WIDE
    data (the desktop overview shows YOUR personal data).

🤖 2. THE BOTS
================================================================================

BUILT-IN BOTS (ship in the app, also run on Oracle):
  • LONG  (longbot_v2.py)  — momentum + mean-reversion portfolio, AI scores/ranks
                             candidates (Claude / Gemini / Groq, Vision on charts).
  • SHORT (shortbot_v2.py) — bear-momentum short selling.
  • DAY   (daybot.py)      — single high-conviction intraday bracket order
                             (entry + GTC take-profit + GTC stop-loss + stale-
                             bracket safety net + orphaned-position re-arm).
  • UNIVERSE MANAGER (universe_manager.py) — refreshes candidate ticker lists.

CUSTOM / AI-GENERATED BOTS:
  • Built in the MAKE BOT tab by an AI from a strict skeleton (BOT_SKELETON.md).
  • Each bot carries an APEX-BOT-META docstring header: name, description,
    method, ai_used, compatible_models, asset_type, universe, requirements,
    broker.
  • The bot FRAMEWORK (core/bot_framework.py BotRunner) owns all the plumbing so
    AI bots only have to write decide(symbol, bars, position, account) ->
    {action, qty, reason}. The framework handles: yfinance fetch, MultiIndex
    flatten, BTC-USD <-> BTC/USD symbol mapping, MarketOrderRequest, per-symbol
    error isolation, the main loop, the heartbeat sleep, trade-log writing.
  • Example user bot: CRYPTO trend bot (linear-regression trend follower on top
    crypto pairs, 24/7).

HOW A BOT RUNS:
  • LOCALLY  — desktop launches it as a QProcess subprocess.
  • ON ORACLE (cloud) — uploaded to /opt/apex_users/user_<id>/private_bots/ and
    spawned server-side so it keeps trading 24/7 EVEN WHEN THE DESKTOP APP IS
    CLOSED. Cloud bots are never killed on app quit (that's the whole point).
  • Each bot reads its Alpaca slot keys (ALPACA_API_KEY_<SIDE> /
    ALPACA_SECRET_KEY_<SIDE>) — <SIDE> is LONG/SHORT/DAY or the custom bot's slug.

PER-BOT DATA SCOPING (v4.6.28+):
  • Every P/L number a bot shows is scoped to THAT BOT'S LIFETIME, never the
    Alpaca account's history. A brand-new bot shows $0.00 / 0.0% / "new bot".
  • Backed by per-bot snapshots: <slug>_lifetime.jsonl + <slug>_trade_log.jsonl.
  • v4.6.30 fixed custom bots showing no data: core.data lookups were hardcoded
    to LONG/SHORT/DAY; now log_files_for(side)/snapshot_files_for(side) resolve
    files for ANY slug, and BotRunner + the crypto template write a trade-log
    entry on every executed order. Custom-bot tabs now populate Closed Trades +
    equity chart once they trade.

💰 5. ECONOMY
================================================================================

  • Credits = virtual money (1 ◊ = $0.01). Real money conceptually sits in the
    app's bank account; credits track ownership.
  • Buying a bot: ~5% of credits split to admin + running account, rest to the
    seller (ownership of real money changes while money stays in the app account).
  • MAKE BOT "Via APEX" generations cost credits (own AI keys = 0 cost; Via-APEX
    charged per model). Free-tier rate-limit projection shown.
  • Cashout to real fiat (Stripe Connect / Revolut) is NOT built yet — see §7.

🛠️ 6. BUILD / RELEASE PIPELINE (how a version ships)
================================================================================

  1. Edit version.json (version + notes).
  2. tools/embed_version.py (build.bat step 1c) bakes the version into
     apex_version.py, core/_version.py, installer.iss — AND nukes stale
     dist/APEX + build/APEX. Has a --validate-dist guard (APEX.exe > 10MB,
     version.json present + matching).
  3. PyInstaller --onedir -> dist/APEX (APEX.exe ~25MB + _internal/).
  4. Inno Setup (ISCC) -> installer/APEX_Setup.exe (~200MB, per-user install to
     %LocalAppData%\APEX Trading Platform, /VERYSILENT capable).
  5. git commit + push, then gh release create/upload "vX.Y.Z" with the
     installer attached. The in-app updater reads /releases/latest.

RECURRING BUILD GOTCHAS (lessons baked in):
  • ALWAYS gh release create — committing alone doesn't publish.
  • ALWAYS smoke-launch dist\APEX\APEX.exe before releasing.
  • A hung gh upload can lock installer\APEX_Setup.exe, which makes the NEXT Inno
    compile fail with "EndUpdateResource failed (110)" and uploads a stale stub.
    (This bit v4.6.30 — fixed by killing the stale gh PID, deleting the locked
    file, recompiling, re-uploading --clobber.)
  • Force-kill all APEX processes before a silent install or Inno returns exit 0
    without replacing files.

TOOLCHAIN: Python 3.14 (dev) / 3.11 (Oracle), Inno Setup 6 at
"C:\Program Files (x86)\Inno Setup 6\ISCC.exe", gh CLI.
